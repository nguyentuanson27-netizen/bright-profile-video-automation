# Spec 001 Amendment — Review 4914663081

Status: accepted implementation clarification for PR #1.

This amendment resolves the same-canonical provenance ambiguity discovered during production-hardening review. It is part of Spec 001 for the current PR and supersedes the conflicting duplicate-source wording in the original spec where stated below.

## A1 — Coherent same-canonical source observations

For two or more evidence observations whose source URLs canonicalize to the same `canonicalUrl`, the emitted `sources[]` entry must remain traceable to one complete normalized input observation. The normalizer must not synthesize a source by combining conflicting title, publisher, author, publication date, excerpt, source type, or source-relationship fields from different observations into a provenance combination that no caller supplied.

Selection among same-canonical observations must be deterministic and input-order independent. V1 uses one fixed total order over the complete normalized observations:

1. greater explicit provenance completeness;
2. earlier explicit `publishedAt` when completeness ties, so freshness is conservative;
3. stronger existing source-type prior;
4. stronger existing source-relationship prior;
5. longer supporting excerpt;
6. lexical raw URL and full normalized-observation tie-breaks.

The selected record is emitted as a whole observation. Complementary metadata or a longer excerpt from a losing same-canonical observation is not copied into the winner when doing so would create synthetic cross-observation provenance.

This amendment **supersedes Spec 001 Step 6** bullets `prefer non-null metadata` and `keep the longest directly supporting excerpt` **only for fields belonging to multiple observations of the same canonical source URL**. Those bullets continue to apply where they do not violate provenance coherence, including compatible evidence-level metadata enrichment. Distinct canonical source URLs are still unioned and preserved subject to the separately accepted >20-source overflow amendment.

## A2 — Health-route connection boundary

`GET /health` is intentionally outside the application rate-limit bucket, but it is still an unauthenticated HTTP boundary. Because it returns before MCP body collection, the server must not leave a body-bearing keep-alive health request waiting indefinitely for an incomplete declared body. The health response must terminate that connection after the response is flushed (or provide an equivalent bounded body/deadline policy).
